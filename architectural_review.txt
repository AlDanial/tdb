  Architectural review of tdb

  I read 8k LOC across the package, mapped imports, counted state-guards, and identified the seams worth straightening. Below are
  findings ranked by impact on future maintenance and feature velocity, with concrete recommendations. I'm calling out trade-offs
  because some changes are bigger than they look.

  What's already healthy

  Worth naming first so the recommendations land in context:

  1. Clean three-layer split between dap/, session/, server/ + widgets/. The DAP client is genuinely independent of textual.
  2. Event-handler protocol (session/event_bus.DebugEventHandler) with a CompositeEventHandler for dual TUI+server mode is the
  right shape. This is what makes headless mode possible at all.
  3. DAPClient is already a thin, mockable wrapper (Future-returning send, event subscriptions, no UI coupling). Test-friendly.
  4. DAP types are dataclass round-trip-safe — from_dict/to_dict are uniform.

  The architecture has good bones. The recommendations are about firming up seams that are already implied by the design.

  Findings, ranked by impact

  1. app.py is a 2,011-line god class — split it

  TdbApp has ~80 methods mixing five concerns:

  - DAP event handlers (on_dap_*)
  - Widget message handlers (on_code_view_*, on_breakpoint_view_*, …)
  - Modal lifecycle (open file, traceback, keybindings, about, doc, quit)
  - Async-tasks / threads / processes inspection workflows (~250 lines each)
  - Top-level keyboard actions (action_*)

  Recommendation: extract collaborator objects that the App owns and forwards to. Suggested split:

  ┌──────────────────────────────────────┬───────────────────────────────────────────────────────────────────────────────┐
  │              New module              │                                     Owns                                      │
  ├──────────────────────────────────────┼───────────────────────────────────────────────────────────────────────────────┤
  │ app_handlers/dap_event_handler.py    │ every on_dap_* method (already a coherent subset)                             │
  ├──────────────────────────────────────┼───────────────────────────────────────────────────────────────────────────────┤
  │ app_handlers/widget_dispatcher.py    │ every on_<widget>_* message handler                                           │
  ├──────────────────────────────────────┼───────────────────────────────────────────────────────────────────────────────┤
  │ app_handlers/modal_controller.py     │ open-file / traceback / quit-confirm / keybindings / about / docs             │
  ├──────────────────────────────────────┼───────────────────────────────────────────────────────────────────────────────┤
  │ app_handlers/inspection_workflows.py │ the ~750 lines of threads / processes / async-task fetch+modal logic          │
  ├──────────────────────────────────────┼───────────────────────────────────────────────────────────────────────────────┤
  │ app.py                               │ composition root only — compose(), mounts, theme/keybinding wiring, lifecycle │
  └──────────────────────────────────────┴───────────────────────────────────────────────────────────────────────────────┘

  This is a refactor, not a rewrite. Each method already takes self only — moving them to a collaborator that holds a reference to
   self.controller and self.app is mostly cut/paste plus message re-emission.

  Why it's high-impact: every new feature today (e.g., a new modal, a new widget, a new DAP event) touches this one file. Future
  refactors fight git's merge resolution because everything is co-located. Split would also let you write focused unit tests for
  inspection workflows without spinning up Textual.

  2. Server pulls UI modules — break the headless-imports-Textual chain

  server/app.py lines 15–16:

  from tdb.widgets.async_tasks_modal import TASK_COLLECT_EXPR, TASK_LOCALS_EXPR, parse_task_json
  from tdb.widgets.processes_modal import PROCESS_COLLECT_EXPR, parse_process_json

  This means tdb --headless imports Textual (transitively, via widgets.*_modal). Headless mode is supposed to be the lightweight
  RPC entry point; importing the whole TUI framework defeats that.

  Recommendation: extract TASK_COLLECT_EXPR, parse_task_json (and the process equivalents) into a new module tdb/inspection.py or
  tdb/session/inspection_exprs.py. Both the modals and the server import from there. Pure data + parsing, no UI.

  This is a 30-line move with no behavior change. After this, you can verify: python -c "import tdb.server.app" should not import
  textual.

  3. Server create_app is a 500-line closure — flatten it

  server/app.py:create_app defines 24 inner async functions, then collects them into a dict at line 492:

  def create_app(controller_ref, handler) -> FastAPI:
      def _ctrl() -> DebugController: ...
      async def _set_breakpoint(params): ...
      async def _remove_breakpoint(params): ...
      # ... 22 more inner fns ...
      _actions: dict[str, Any] = {"set_breakpoint": _set_breakpoint, ...}

  Closures-as-actions is fine for 3 actions; at 24 it's just hidden cohesion. Each handler is a self-contained "given a controller
   + handler + params, return RpcResponse" function. They're shadowing themselves.

  Recommendation: extract to a class:

  class RpcHandlers:
      def __init__(self, controller_ref, handler): ...
      async def set_breakpoint(self, params): ...
      async def status(self, params): ...
      # ...

  def create_app(handlers: RpcHandlers) -> FastAPI:
      app = FastAPI(...)
      actions = {name: getattr(handlers, name) for name in PUBLIC_ACTIONS}
      @app.post("/rpc")
      async def rpc(req): return await actions[req.action](req.params)
      return app

  Now you can unit-test each RPC handler directly without spinning up uvicorn — currently every server test must subprocess-out,
  taking 28 seconds for 16 tests. With a class, half of those tests collapse to in-process unit tests.

  4. Two parallel DAP-event delegation chains — collapse to one

  Today's flow when stopped fires:

  DAPClient._read_loop
    → controller._on_stopped (sync)         <-- updates _active_client
      → event_handler.on_stopped(...)
        ├─ TextualEventHandler.on_stopped
        │   → app.post_message(DapStopped(...))
        │     → app.on_dap_stopped (async)   <-- updates state.is_running, state.stop_reason, fetches stack
        └─ ServerEventHandler.on_stopped
            → set stopped_event, broadcast SSE
              ← later: server._step_action awaits stopped_event
                → _sync_state_from_stop()    <-- updates state.is_running, state.stop_reason

  Two consumers each duplicating state mutation. We just fixed _on_terminated because of exactly this asymmetry. The same shape is
   in _on_stopped and _on_continued:

  ┌───────────────────┬─────────────────────┬─────────────────────┬────────────────────────────────────────┐
  │       Field       │ Set in _on_stopped? │ Set in TUI handler? │ Set in headless _sync_state_from_stop? │
  ├───────────────────┼─────────────────────┼─────────────────────┼────────────────────────────────────────┤
  │ is_running        │ ❌                  │ ✅                  │ ✅                                     │
  ├───────────────────┼─────────────────────┼─────────────────────┼────────────────────────────────────────┤
  │ stop_reason       │ ❌                  │ ✅                  │ ✅                                     │
  ├───────────────────┼─────────────────────┼─────────────────────┼────────────────────────────────────────┤
  │ current_thread_id │ ❌                  │ ✅                  │ ✅                                     │
  └───────────────────┴─────────────────────┴─────────────────────┴────────────────────────────────────────┘

  _sync_state_from_stop exists because the producer doesn't set state. It's a smell — every consumer that talks to a
  DebugController must remember to call it after a wait_for_stop().

  Recommendation: make the controller's DAP event handlers the single state authority. Set state.is_running, state.stop_reason,
  state.current_thread_id in _on_stopped. Set is_running=True in _on_continued. Then delete _sync_state_from_stop from
  server/app.py and the redundant assignments from app.on_dap_stopped/on_dap_continued/on_dap_terminated. Consumers shrink to
  "wait for the event, then read state."

  This is the same refactor as the termination fix, applied uniformly. Audit count to retire: 5 redundant state.is_running = ...
  sites and 3 state.stop_reason = ... sites.

  5. Guard repetition: if state.is_terminated: ... × 52

  Across controller.py (12), server/app.py (20), app.py (20). Three patterns dominate:

  # pattern A: skip DAP send
  if self.state.is_ready and not self.state.is_terminated:
      await self.client.set_breakpoints(...)

  # pattern B: RPC error
  if _ctrl().state.is_terminated:
      return RpcResponse.error("Program has terminated")

  # pattern C: TUI guard against crash
  if self.controller.state.is_terminated or self.controller.state.is_running:
      return

  Each pattern is correct in isolation but has drifted (some check is_running, some don't; some check is_post_mortem, some don't).
   When you add a fourth state (e.g., is_attaching, is_disconnecting), you'll have to find and update all 52 sites.

  Recommendation: a small state-machine wrapper.

  # session/state.py
  class SessionPhase(Enum):
      NOT_STARTED = auto()
      LAUNCHING = auto()
      RUNNING = auto()
      STOPPED = auto()
      TERMINATED = auto()
      POST_MORTEM = auto()

  @dataclass
  class DebugState:
      phase: SessionPhase = SessionPhase.NOT_STARTED
      # ...

      @property
      def can_send_dap(self) -> bool:
          return self.phase in (SessionPhase.RUNNING, SessionPhase.STOPPED)

      @property
      def can_step(self) -> bool:
          return self.phase == SessionPhase.STOPPED

      @property
      def is_terminated(self) -> bool:  # back-compat
          return self.phase == SessionPhase.TERMINATED

  Replace pattern-A guards with if state.can_send_dap, pattern-B with if not state.can_step. The transitions become explicit
  (state.transition_to(STOPPED) from _on_stopped), which makes the bug we just fixed structurally impossible: you can't forget to
  set state if you're calling transition_to.

  Trade-off: this is a wider refactor (~2 days). If you do only one thing on this list, #1 has higher leverage; this is a "do
  later, after #1 settles."

  6. RPC actions don't survive controller swap consistently

  ControllerRef exists exactly because the TUI replaces controller on restart. But the server holds two references: controller_ref
   (mutable) and handler (the ServerEventHandler instance — fixed for the life of the FastAPI app). On restart, _restart_session
  rebuilds the controller and the event handler, then calls self._controller_ref.set(...). But the server's handler reference
  still points at the old ServerEventHandler, which still has its old asyncio events and SSE subscribers.

  Look at app.py:792-805:

  self._textual_handler = TextualEventHandler(self)
  if self._server_handler is not None:
      from tdb.session.event_bus import CompositeEventHandler
      self._server_handler.initialized_event.clear()
      self._server_handler.stopped_event.clear()
      # ... 6 manual-clear lines

  Manual reset of internal asyncio.Event state because we can't replace the handler. SSE subscribers from before the restart will
  keep their queues but receive no further events from the new session… actually I'd want to read more closely to be sure, but
  it's a smell.

  Recommendation: introduce a HandlerRef symmetric with ControllerRef, OR — better — make ServerEventHandler.reset() an explicit
  operation that does the 6 lines + republishes a "session-restart" SSE event so subscribers know to reconnect their state. This
  also gives integration tests a clean way to assert restart semantics.

  7. controller._is_remote_attach is leaking into UI logic

  src/tdb/app.py:779:        if new_program is None and self.controller._is_remote_attach:
  src/tdb/app.py:922:        if not self.controller._is_remote_attach:
  src/tdb/app.py:956:                can_restart=not self.controller._is_remote_attach,
  src/tdb/app.py:1044:                can_restart=not self.controller._is_remote_attach,

  The TUI is reaching into a controller private to make policy decisions ("can I restart? can I step out?"). This should be a
  capability the controller exposes:

  class DebugController:
      @property
      def supports_restart(self) -> bool:
          return not self._is_remote_attach

      @property
      def is_remote_attach(self) -> bool:
          return self._is_remote_attach

  Same for controller._child_clients.get(pid) (app.py:1414, 1888) — should be controller.get_child_client(pid).

  These are tiny changes (one afternoon) but they uncouple the layers. Once tdb grows a third entry mode (e.g., the deferred
  multi-call breakpoint hook, or a "frozen heap" mode somewhere between live and post-mortem), you'll add _is_X flags and the
  leaks proliferate.

  8. Test surface gaps

  Now that tests exist, the next layer of debt is what they can't easily reach. Specifically:

  - No DebugController unit tests at all. The whole controller is integration-only because start() requires debugpy. You can fix
  this by injecting DAPClient instead of constructing it: DebugController(handler, client_factory=DAPClient) lets tests pass a
  fake client that returns canned responses. The controller has 800 LOC and is the most logic-dense layer in the package — it
  deserves dedicated tests.
  - No widget tests. Textual has App.run_test() for snapshot testing widgets in isolation. CodeView's executable-line computation,
   breakpoint gutter rendering, search/paragraph movement — all testable without the full app.
  - Integration tests are subprocess-based. As noted in #3, half of these can be in-process if RpcHandlers is a class. You'd 5x
  the integration-test speed.

  9. Smaller cleanups that reduce surprise

  These are individually small but each one is a future-time-saver:

  - /tmp/tdb.log is hardcoded in cli.py:165. On Windows that path doesn't exist; on shared hosts it's a security/permissions
  issue. Use CONFIG_DIR / "tdb.log" (you already have the cross-platform config dir resolver).
  - load_breakpoints(program=None) is a "legacy flat format" path kept around as a migration artifact but no caller uses it
  (verified). Delete the branch and its docstring caveat.
  - _TerminalSpec map in controller.py:25-35 lives next to a method that uses it. Move to a terminals.py so adding a new terminal
  doesn't churn controller.py.
  - CLI breakpoint parsing is in cli.py; RPC breakpoint parsing is in server/app.py:_set_breakpoint (basically the same logic).
  Extract parse_file_line(spec) once.
  - _unquote_dap_string in app.py:1997 is a pure utility floating alone in a 2k-line file; move to dap/types.py or a new
  dap/util.py.
  - pyproject.toml now lists httpx twice in the dev extras (once explicitly, once duplicated); harmless but worth a one-line fix.

  Suggested sequencing

  If you tackle these, the order that minimizes rework:

  1. #2 (server-imports-widgets) — 30-minute fix, frees you to do clean tests.
  2. #3 (RpcHandlers class) — half a day, immediately speeds up the test loop.
  3. #7 (controller capability properties) — afternoon, lets #1 split cleanly.
  4. #1 (split app.py) — multi-day; biggest payoff but invasive.
  5. #4 (controller as state authority) — natural follow-up to the recent termination fix.
  6. #5 (SessionPhase state machine) — only worth doing once #1 + #4 are done; otherwise you'd refactor twice.
  7. #6 (HandlerRef), #8 (controller unit tests), #9 (cleanups) — opportunistic.

  One thing not to do

  Don't introduce a generic plugin/extension system yet. I can see the temptation — there are 5 inspector workflows
  (threads/processes/tasks + breakpoints + variables) that all share the "fetch via DAP evaluate, parse JSON, render in modal"
  shape. There's a real abstraction lurking there. But the three modal implementations (async_tasks_modal, processes_modal,
  threads_modal) are still small enough (250–350 LOC each) that the abstraction would cost more than it saves until you grow a
  fifth one. Revisit when you add async-iterator inspection or coroutine state.

  What I'd want to know more about

  If you want a deeper dive on any of these, the highest-uncertainty areas are:

  - Restart and SSE subscriber lifecycle (#6) — I'd want to actually trace a restart with subscribers attached to confirm whether
  they get stale or auto-recover.
  - Widget message types & propagation — I scanned but didn't deeply trace all on_<widget>_* paths in app.py. Some may be
  cross-cutting in ways that resist a clean #1 split.
